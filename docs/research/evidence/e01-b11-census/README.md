# E01 B11 — pinned-CLI census observations for owned CIFF, small formats and container stubs

Batch B11 records CRW, BMP, GIF and TGA against owned synthetic fixtures, plus header-only stubs for
QuickTime (one brand in `qTimeFileType`, one not), Matroska, RIFF/AVI, RIFF/WAV and ASF. 95 census
rows: 87 observed through the pinned Exiv2 0.28.9 CLI (`b0859fc61`, built in CI with the pinned option
set) and 8 recorded `blocked` for the Canon vendor-private CIFF region no reviewed document describes.
Every row keeps `verification: not-assessed`, the denominator stays unfrozen, and no coverage
percentage is computed anywhere in this batch. The gate for this batch is
`docs/research/E01_B11_RIGHTS_AND_ORACLE_REVIEW.md`.

Files here:

- `observations.json` — the recovered CI report (run 42757620226, job *Exiv2 0.28.9 / bounded E01 B11
  container and small-format observations*, head `c34ee5e5d`). There is no local counterpart: this
  sandbox has no cmake/ninja or expat/zlib headers, cannot install them, and cannot reach the Actions
  log or the artifact-blob host, so CI runs are the only observation source. The payload was recovered
  from the job's check-run annotations (`gh api repos/sensboston/MetadataSharp/check-runs/129635560547/annotations
  --paginate`), five `B11Z observations.json i/5` chunks plus their `count` marker, concatenated in
  index order, base64-decoded and inflated once. `receipt.json` records both digests and the chunk
  arithmetic; it is generated by `tools/reference/write_b11_receipt.py`, never hand-written.
- `receipt.json` — provenance, the tally, the recovery record, and the four observation-shaped findings:
  the CIFF print form, the `-et` shapes, the fixtures the factory never handed to a reader, and the
  reproduction status.
- `../e01-b11-preflight/observations.json` — the preflight for the same head. It is the only place the
  stdout *text* lives (the census rows carry digests), so this is where `ciff-mapped-v1 -pe`'s eleven
  printed entries and the AVI stub's four `Xmp.video.*` keys can be checked without re-running anything.
- `../e01-b11-preflight/prior-run-observations.json` — the previous run's preflight (42757054570 at
  `822fb1d`), kept as the reproduction sample. Its 107 records are byte-identical to the committed
  payload's; the differing sections are `baseline` (the build embeds its own timestamp, and two
  `library=` lines in the version banner also swap order), `secondary` (ExifTool's `System:File*Date`)
  and `sourceCommit`. Observations are reproducible; the compiled reference binary is not.

## What this batch changes about the record

- `-et` is not "the byte count". It is `Extract::writeThumbnail`'s return
  (`app/actions.cpp:823-864`), which is a byte count only on the path that writes a thumbnail:
  `137` for the two CRW layouts that carry a `0x2008` component, `0` plus "Image does not contain an
  Exif thumbnail" for `ciff-mapped-v1`, and `-3` — surfacing as **253** because `main` returns
  `static_cast<unsigned int>(returnCode) % 256` (`app/exiv2.cpp:195`) — for `ciff-unmapped-only-v1`.
  The review document asserted `exitCode == artifactBytes` for all four rows; the observation disagreed
  on one, so the rule was corrected and the recorder now labels the shape instead of carrying a
  standing finding. The discovery test derives the shape from the CLI's own wording, so it does not
  depend on the label's name.
- Six cleared fixtures were never handed to a reader: both BMPs, both MOVs, MKV and WAV all came back
  `kerFileContainsUnknownImageType` from `ImageFactory::open` (`src/image.cpp:825-830`) even though
  each format's magic test matches at offset 0. This directory records the refusal, not a reason: the
  two candidate causes are the `Image::good()` re-check inside each `newXInstance`
  (`src/image.cpp:713-718`) and an earlier registry entry matching first, and one CI run cannot tell
  them apart. Nothing here says BMP, QuickTime, BMFF or Matroska is unsupported.
- `-pS` and `-pC` refused for all 17 fixtures, so the batch contains no structure print at all —
  including for the MOV that BMFF's `printStructure` override would otherwise have reached.

## Limits, restated so they travel with the bytes

Fixtures are authored containers, not camera captures; a refusal is not evidence a format is
unsupported and a success is not evidence metadata support works; no MetadataSharp code is exercised;
no write sub-operation is attempted, so the symmetric CRW encoder is neither claimed nor refuted; no
video metadata family is enumerated because the pinned table claims none; ExifTool is a secondary
reference, never an oracle. `TZ=UTC0` is pinned on the job and `utcOffsetSeconds` is recorded per
record, because `CrwMap::decode` renders `0x180e` through `localtime_r` and the printed
`Exif.Photo.DateTimeOriginal` is only reproducible with the offset on the record.
