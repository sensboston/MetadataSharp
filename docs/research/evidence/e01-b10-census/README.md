# E01 B10 — pinned-CLI census observations for TIFF-derived RAW wave 2

Batch B10 records MRW, RW2, SR2 and RAF against owned synthetic fixtures. 64 census rows:
32 observed through the pinned Exiv2 0.28.9 CLI (`b0859fc61`, built in CI with the pinned
option set) and 32 recorded `blocked` for the vendor-private structures no reviewed document
describes. Every row keeps `verification: not-assessed`, the denominator stays unfrozen and
no coverage percentage is computed anywhere in this batch. The gate for this batch is
`docs/research/E01_B10_RIGHTS_AND_ORACLE_REVIEW.md`.

Files here:

- `observations.json` — the recovered CI report (run 42742515073, job
  *Exiv2 0.28.9 / bounded E01 B10 wave-2 RAW observations*, head `a147cf2`). There is no
  local counterpart: this sandbox has no cmake/ninja or expat/zlib headers, cannot install
  them, and cannot reach the Actions log or artifact-blob hosts, so CI runs are the only
  observation source. `docs/research/evidence/e01-b10-preflight/observations.json` holds the
  preflight report, which is where the stdout *text* lives (the census rows carry stdout
  digests only).
- `ci-observations.json` — the same recorder re-run in CI on the next head (run 42744015517 at
  `4322b70`), kept as the cross-run reproduction sample. The two payloads agree section-for-section
  on `observations`, `blocked`, `fixtureManifest` and `outcomeCounts`, and differ only in `baseline`
  (the build embeds its own timestamp, so `executableSha256` moves while `cmakeCacheSha256` and the
  effective CMake options do not), `sourceCommit`, and the `System:File*Date` fields ExifTool stamps
  into the secondary block. The claim stays as bounded as B9's: observations are reproducible, the
  compiled reference binary is not.
- `master-observations.json` — the third sample: the recorder re-run by the post-merge master push
  (run 42747632654 at `e7b0ec8`), i.e. the merged tree re-observing the committed evidence. Its
  observation payload matches both earlier runs byte-for-byte; it is recorded in
  `receipt.json` under `reproduction.masterComparison` rather than merged into the cross-run
  block, so a third run cannot overwrite the second one's record.
- `receipt.json` — provenance, both annotation-recovery records and their hashes, the
  baseline digests, the tally, the per-format print forms, the annotation-budget finding, the
  `reproduction` record and the `notClaimed` list. It is generated by
  `tools/reference/write_b10_receipt.py`, which recomputes every digest from the committed
  files, so a re-run regenerates the receipt instead of re-typing it.

## What ran

One read-only command per row, chosen by family (`-pS` inventory, `-pa` exif/iptc/xmp and
thumbnail reads, `-pc` comments, `-pC` icc, `-et` thumbnail extract), against a copy of the
fixture in a scratch directory, then ExifTool 12.76 `-json -G1 -s` as a secondary reference
on the same bytes. No pixels are decoded, nothing is written back to a fixture, no MakerNote
is interpreted, and no vendor-private structure is invented.

| Format | Result |

| RAF (`owned-raf-fujifilm.raf`) | `-pS` accepted, 846 bytes: the header field map prints exactly the offsets this fixture authors (JPEG 108/698, CFA 1258/64, TIFF 806/452). `-pa` accepted, 1941 bytes with both tokens, i.e. the embedded camera-settings TIFF **is** read. `-pc` accepted and printed 14 bytes = `B10RafComment\n` — the preview JPEG's comment really does reach `-pc`, which the review had left open. `-pC` accepted with an **empty** print: the authored ICC sits in the camera-settings TIFF and never becomes the image's profile. `-et` exited 0 and wrote nothing ("Image does not contain an Exif thumbnail"). This is the finding, not a defect: the pinned registry has no SR2 entry, so no SR2-specific observable exists to record. |

Aggregate: 26 `accepted`, 2 `nonzero-exit-artifact-produced`, 2 `zero-exit-no-artifact`, 2
`refused`, 32 `blocked-rights`, 0 `scan-changed`, 0 `static-not-applicable`; every input
byte-identical afterwards; 2 artifacts produced in scratch space, none in the repository.

Three rules this batch had to state rather than assume:

* **The `-et` exit code is a byte count.** In this build the status *is* the number of bytes
  the CLI wrote, so `rc == artifactBytes` is asserted per row and holds on all four extract
  rows — including the two that produced nothing (0 == 0). That is why a zero exit with no
  artifact gets its own label, `zero-exit-no-artifact`, instead of reading as a success or as
  a refusal. No row was classified by the sign of the exit code.
* **The four `-pa` rows on a layout share one stdout digest.** Exif, IPTC, XMP and thumbnail
  reads all ask for `-pa`, so they print identical bytes; none of them is an independent
  per-family claim. On RAF and RW2 that sharing is load-bearing: RAF's IPTC/XMP print is the
  *same* `-pa` text plus the "Ignoring …" warnings, and RW2's is the same *absence*.
* **A 202-byte ICC print is a banner, not a bigger profile.** `Rw2Image::printStructure`
  prints `RW2 IMAGE` before delegating (`src/rw2image.cpp:63`), and 9 characters plus a newline
  is the whole difference. This also settles B9's unanswered ORF row: `OrfImage::printStructure`
  prints `ORF IMAGE` at `src/orfimage.cpp:55`, which is where its 202 came from. B9's recorded
  rows are not rewritten — the anomaly stays in its own evidence, corrected by cross-reference.

## What the secondary reference showed

ExifTool 12.76 (pinned `212f02cf2`) exited 0 on all four fixtures. Its classifications:
`File:FileType MRW` / `image/x-minolta-mrw`, `SR2` / `image/x-sony-sr2`,
`RAF (M-RAW)` with `ExifTool:Warning: Error reading M-RAW header`, and — for the RW2 fixture —
`File:FileType RAW` / `image/x-raw`, i.e. it did **not** classify the authored `II`+`0x0055`
header as RW2. It also reports `IFD0:Artist = B10Artist` for that same file, the tag the
pinned CLI's pana mapping does not surface, and `Composite:ImageSize 17481x17440` for the MRW
fixture, a size derived from this file's authored block lengths. None of that is a
validity judgement: ExifTool's file-type lookup consults the extension, and these are authored
containers, so every one of these rows is recorded as `secondary-observation-not-conformance`.

## What is *not* shown

These fixtures are authored containers with owned metadata carriers. They contain no
vendor-private raw data, no MakerNote, no decodable raw pixels and no real camera preview.
Therefore:

- an accepted `-pa` here is not evidence that the vendor layout is supported;
- RW2's empty `-pa` token set is not evidence that an RW2 capture has no Artist tag — it is
  evidence about this build's print path for this container;
- the one-newline `-pc` prints are not evidence that a real capture has no comment;
- MRW's `kerUnsupportedImageType` refusals are not evidence the file is corrupt: they are the
  documented absence of a structure print for that image type;
- `blocked-rights` never means unsupported; the vendor-private cells stay visible as blocked;
- nothing here verifies MetadataSharp, freezes a denominator, or grants a write contract.

## How the evidence was recovered, and the trap in it

Both reports arrive as chunked `::notice` annotations on the job's check run
(`B10Z observations.json i/4` for the census report, `B10RAW …` for the preflight, each with a
trailing `… count::N` marker). Recovery is: concatenate the chunk bodies **in index order**,
then base64-decode, then inflate **once**. Per-chunk inflation raises `zlib.error -5` and looks
exactly like GitHub truncation — that false lead cost this project a batch's worth of
investigation twice, so it is written down here rather than rediscovered. The job used 11
annotations of the 50-per-check-run cap; the cap drops overflow silently, which is why B10 has
its own job (`pinned-exiv2-b10`) instead of steps appended to `pinned-exiv2-baseline`.

One more platform trap belongs in this record, and it took three pushes to exhaust. The digests
here are taken over *committed* bytes, and Windows runners check text out with
`core.autocrlf=true`, which rewrote these LF files to CRLF and broke the discovery suite on
`net8.0`/`net10.0` only (run 42744015517). `.gitattributes` now pins
`docs/research/evidence/**/*.json text eol=lf` for the whole evidence tree — earlier batches
pinned one file at a time — and the failure is reproducible without a Windows box:
`git -c core.autocrlf=true checkout-index -a -f --prefix=/tmp/wc/`, then hash the result.

The *guard* for that pin then failed on Windows as well (run 42746390202), because it had been
parsing `git check-attr` output that does not parse there, so every evidence file looked unpinned:
a platform-fragile test pretending to protect against platform fragility. It now asserts two
things — that the rule is present in `.gitattributes`, and that each hashed evidence file still
equals its own blob in `HEAD` — so it bites on Linux, macOS and Windows alike. Diagnosing it cost
two CI round trips for a second reason: the Python steps published no failure detail anywhere
readable from here, so they now tee their output and an `if: failure()` step turns the `FAIL:` and
`AssertionError` lines into annotations, mirroring what the .NET trx step already does.
